# ArbiCore X — v1.0.2 Release Notes

**Release date:** 2026-02-05
**Status:** Production-ready. Recommended for all deployments.
**Upgrade urgency:** **HIGH** — v1.0.1 shipped with a latent build-time bug
that produces a black-screen operator UI in production.

---

## TL;DR

Fixes the "black screen" operator UI reported against v1.0.1 by threading
`REACT_APP_BACKEND_URL` (and its Vite twin `VITE_BACKEND_URL`) through the
Docker build correctly, and adds a **triple-layer guardrail** so this
class of bug can never silently reach production again.

If you deployed v1.0.1 and see a black screen at your ArbiCore X domain,
you need this release.

---

## Root cause

CRA (operator UI) and Vite (Opportunity Center) both replace their
`process.env.REACT_APP_*` / `import.meta.env.VITE_*` references at
**compile time**, not runtime. Whatever value those variables hold during
`yarn build` is BAKED into the static JS bundle for the life of the image.

In v1.0.1, the failure chain was:

1. **`deployment/docker/frontend/Dockerfile`** never declared
   `ARG REACT_APP_BACKEND_URL` or promoted it to `ENV`, so the compose
   `build.args` block was silently ignored by Docker at build time.
2. `yarn build` therefore ran with `process.env.REACT_APP_BACKEND_URL`
   undefined.
3. Webpack minified `` `${undefined}/api` `` into the literal string
   `"".concat(void 0,"/api")` — appearing 26 times across the bundle
   (once per file that constructs the API base URL).
4. At runtime, the browser interpreted `undefined/api/auth/status` as a
   *relative* URL and resolved it against the SPA origin
   → `https://<your-domain>/undefined/api/auth/status`
   → nginx SPA fallback returned `index.html` with HTTP 200 and
     `Content-Type: text/html`.
5. `axios` parsed the HTML string as JSON, and the auth context set
   `user = "<!DOCTYPE html>…"` — a truthy string.
6. `<ProtectedRoute>` mounted `<Dashboard>`. Downstream hooks called
   `data.something.map(…)` on the HTML string → `TypeError` → React
   error boundary → **blank body over the terminal-theme black
   background** → apparent "black screen".

The exact same bug applied to `docker-compose.shared.yml`, which also
lacked a `build:` block entirely, and to the Opportunity Center
Dockerfile which never declared `ARG VITE_BACKEND_URL`.

---

## Empirical proof

Bundle compiled **without** `REACT_APP_BACKEND_URL`:
```
$ grep -c '"".concat(void 0,"/api")' build/static/js/main.*.js
26
```

Bundle compiled **with** `REACT_APP_BACKEND_URL=https://arbicore.example.com`:
```
$ grep -c '"".concat(void 0,"/api")' build/static/js/main.*.js
0
$ grep -oE '.{0,10}arbicore\.example\.com.{0,20}' build/static/js/main.*.js | sort -u
("https://arbicore.example.com","/api"),AE=…
("https://arbicore.example.com","/api"),AK=…
…
```

Both runs are reproduced in the v1.0.2 test evidence bundled with the
release archive (see `docs/releases/v1.0.2-evidence.txt`).

## What changed

### Files modified

| File | Change |
|---|---|
| `deployment/docker/frontend/Dockerfile` | Declare `ARG REACT_APP_BACKEND_URL`. Hard-fail with actionable message if empty. Promote to `ENV`. Add post-build grep guard that fails if `"".concat(void 0,"/api")` or `undefined/api` appears in the compiled bundle. |
| `deployment/docker/opportunity_center/Dockerfile` | Same treatment for `VITE_BACKEND_URL`. Post-build guard scans `dist/assets/`. |
| `deployment/compose/docker-compose.shared.yml` | Add `build:` block for `frontend` and `opportunity_center` (previously image-only). Uses `${REACT_APP_BACKEND_URL:?…}` — compose fails fast with our custom error if the variable is missing. Removed obsolete top-level `version:` key. |
| `deployment/compose/docker-compose.yml` | Change `${REACT_APP_BACKEND_URL:-https://localhost}` (soft default) to `${REACT_APP_BACKEND_URL:?…}` (hard requirement) — the old soft default silently produced a broken bundle whenever operators forgot the variable. |
| `deployment/compose/.env.shared.example` | Add `REACT_APP_BACKEND_URL=` as a new REQUIRED variable at the top of the file, with inline documentation. Rewrite section 5 (Image Tags) to reflect that the shared profile can now build in-place. Bump default image tags to `1.0.2`. |
| `VERSION` | `1.0.1` → `1.0.2`. |

### The triple-layer regression guard

The user asked for a CI/build guard to prevent this from ever recurring.
v1.0.2 ships three independent layers, any one of which will halt the
build:

1. **Compose interpolation guard** — `${REACT_APP_BACKEND_URL:?<msg>}`
   in both compose files means `docker compose config`, `docker compose
   build`, and `docker compose up` all exit non-zero with a human
   message before Docker is even invoked.
2. **Dockerfile pre-build guard** — first `RUN` in the build stage
   checks `[ -z "$REACT_APP_BACKEND_URL" ]` and `exit 1`s with a
   framed error box explaining how to pass the arg. Catches direct
   `docker build --build-arg` invocations that bypass compose.
3. **Dockerfile post-build guard** — after `yarn build` / `vite build`,
   greps the compiled output for the fingerprint of an unbaked env var
   (`"".concat(void 0,"/api")` for CRA, `undefined/api` for Vite). If
   Webpack or Vite ever changes its emit pattern such that layers 1 and
   2 are bypassed, this final check catches it. Verified by
   deliberately breaking the build and confirming the guard triggers.

## New required environment variables

### Shared-infrastructure profile (`.env.shared`)

You MUST set this variable **before** building the images:

```env
# REQUIRED — Public URL where the operator UI will be reachable.
# CRA/Vite bake this into the JS bundle at BUILD time. NOT runtime.
REACT_APP_BACKEND_URL=https://arbicore.example.com
```

The same value is auto-propagated to the Opportunity Center's
`VITE_BACKEND_URL` — you only set it once.

### Greenfield profile (repo-root `.env`)

Same variable, same behavior. Previously optional with a
`https://localhost` soft default — now REQUIRED. Add to `.env`:

```env
REACT_APP_BACKEND_URL=https://arbicore.example.com
```

## Upgrade steps — Contabo VPS (shared-infrastructure profile)

Run every step on the VPS.

### 1. Pull v1.0.2

Choose ONE of the two paths depending on how v1.0.1 got onto the VPS.

**a) If you deployed v1.0.1 by unpacking a tarball:**
```bash
cd ~   # or wherever your v1.0.1 checkout lives
tar tvzf arbicore-x-v1.0.2.tar.gz | head           # sanity check contents
tar xzf arbicore-x-v1.0.2.tar.gz -C /tmp
rsync -a --delete /tmp/canonical_repo/ ~/arbicore-x/
cd ~/arbicore-x
cat VERSION    # should print 1.0.2
```

**b) If you deployed via git:**
```bash
cd ~/arbicore-x
git fetch --tags
git checkout v1.0.2
cat VERSION    # should print 1.0.2
```

### 2. Update `.env.shared`

```bash
cd ~/arbicore-x/deployment/compose

# Diff against the new example to spot what's new (REACT_APP_BACKEND_URL):
diff .env.shared .env.shared.example | grep -B1 -A2 REACT_APP_BACKEND_URL

# Add the required variable:
grep -q '^REACT_APP_BACKEND_URL=' .env.shared \
  || echo 'REACT_APP_BACKEND_URL=https://your-domain.tld' >> .env.shared

# Confirm it's set:
grep '^REACT_APP_BACKEND_URL=' .env.shared

chmod 600 .env.shared
```

Replace `https://your-domain.tld` with the exact public URL your peer
Caddy serves ArbiCore X on (protocol + host, no trailing slash, no path).

### 3. Rebuild the two affected services

Backend needs no rebuild — this is a frontend-only fix.

```bash
cd ~/arbicore-x/deployment/compose

# Static validation (should print rendered YAML, exit 0):
docker compose --env-file .env.shared -f docker-compose.shared.yml config \
  | grep -A2 'args:'

# Clean, no-cache rebuild of the two SPAs:
docker compose --env-file .env.shared -f docker-compose.shared.yml \
  build --no-cache --pull frontend opportunity_center
```

If `REACT_APP_BACKEND_URL` is missing, the build will fail immediately
with an actionable error rather than producing a broken image.

### 4. Roll the containers

```bash
docker compose --env-file .env.shared -f docker-compose.shared.yml \
  up -d --force-recreate frontend opportunity_center

docker compose --env-file .env.shared -f docker-compose.shared.yml ps
```

### 5. Verify the fix

**Recommended:** run the v1.0.2 deployment verification harness — it
covers the 8-category release checklist automatically.

```bash
cd ~/arbicore-x

# One-time setup for the browser-based checks (categories 5 and 8):
(cd scripts && npm install && npx playwright install chromium)

# Full 8-category verification (positional order is not important):
make verify \
    DOMAIN=https://your-domain.tld \
    PROFILE=shared \
    ADMIN_USER=admin \
    ADMIN_PASS='YOUR_ADMIN_PASSWORD'

# Or shell/API-only (skip Playwright), suitable for hosts without a browser:
make verify \
    DOMAIN=https://your-domain.tld \
    PROFILE=shared \
    SKIP_BROWSER=1
```

The harness exits `0` when all categories PASS, `1` when any FAIL.
Category-level detail (backend health, bundle fingerprint, login flow,
authenticated dashboard mount, …) is printed in colour. See
`scripts/README.md` for full docs.

**Manual fallback** (if you prefer to eyeball it):

```bash
# Confirm the compiled bundle contains YOUR domain, not "void 0":
docker exec arbicore-x-frontend sh -c \
  'grep -oE "\"https?://[^\"]{5,80}\",\"/api\"" \
      /usr/share/nginx/html/static/js/main.*.js \
   | sort -u | head -5'

# Should print your domain, e.g.:
#   "https://arbicore.example.com","/api"

# Any occurrences of the broken pattern? MUST be zero:
docker exec arbicore-x-frontend sh -c \
  'grep -c "\"\".concat(void 0" /usr/share/nginx/html/static/js/main.*.js'
# Expect: 0

# In your browser, load https://<your-domain>/. The Login page must
# render (dark terminal aesthetic, "ARBICORE" wordmark, username/password
# form). Sign in — the Terminal dashboard should mount cleanly.
```

### 6. If anything looks off — rollback

Backend and Mongo are unaffected by this release, so rollback is a
simple retag:

```bash
docker tag arbicore-x-frontend:1.0.1 arbicore-x-frontend:current
docker tag arbicore-x-opportunity-center:1.0.1 arbicore-x-opportunity-center:current
docker compose --env-file .env.shared -f docker-compose.shared.yml \
  up -d frontend opportunity_center
```

## Release verification is now part of the standard checklist

Starting with v1.0.2, `scripts/verify-deployment.sh` (invoked via
`make verify`) is the canonical post-deployment sanity harness. It runs
the 8-category verification matrix below and MUST pass before any
release is declared production-ready — for BOTH greenfield and
shared-infrastructure deployments.

| # | Category | Method |
|---|---|---|
| 1 | Backend health | container running, docker healthcheck healthy, `/api/` returns 200 (internal + public) |
| 2 | Frontend HTTP 200 | operator UI reachable, `<div id="root">` present, JS bundle referenced |
| 3 | Opportunity Center HTTP 200 | analytics SPA reachable (or container `/healthz` fallback) |
| 4 | Bundle verification | compiled bundle contains configured domain, zero `void 0` refs (v1.0.1 regression guard) |
| 5 | Browser runtime | login page renders, no uncaught JS exceptions (Playwright) |
| 6 | API connectivity | `/api/auth/status` returns `200 application/json` (not HTML fallback) |
| 7 | Successful login | `POST /api/auth/login` returns 200 + session; `/api/auth/me` identifies the user |
| 8 | Dashboard render | authenticated navigation to `/` mounts the Terminal dashboard (Playwright) |

Usage:

```bash
make verify DOMAIN=https://your-domain.tld PROFILE=shared \
            ADMIN_USER=admin ADMIN_PASS="$ADMIN_PASS"
```

Full documentation: `scripts/README.md`.
