# v1.0.1 — Patch release

**Release date:** 2026-07-29
**Type:** PATCH (per SemVer, per docs/ROADMAP.md §2)
**Scope:** Runtime-correctness fixes discovered during first Contabo VPS deployment (shared-infrastructure profile). No API changes. No env changes. No schema changes. Fully backward-compatible with v1.0.0.

## Fixed

### Backend build reproducibility outside greenfield installer
- **Symptom:** `docker compose build backend` (used by `docker-compose.shared.yml` operators) fails with `Could not find a version that satisfies the requirement emergentintegrations==0.2.0` — because the backend Dockerfile was COPYing `app/backend/requirements.txt` (the app-side dev file, which references packages only available in the Emergent development environment), instead of `deployment/docker/backend/requirements.prod.txt` (the clean, production-only file).
- **Root cause:** v1.0.0 handled this via a runtime file swap inside `scripts/install.sh`. The swap only runs during greenfield installs; shared-infrastructure operators who invoke `docker compose build` directly never triggered it.
- **Fix:** backend Dockerfile now builds from the repo root and COPYs `deployment/docker/backend/requirements.prod.txt` explicitly. No swap needed. Works uniformly for both profiles.
- **Files:** `deployment/docker/backend/Dockerfile`, `deployment/compose/docker-compose.yml`, `deployment/compose/docker-compose.shared.yml`, `scripts/install.sh` (swap logic removed).

### Frontend + Opportunity Center: reliable non-root nginx
- **Symptom:** `mkdir() "/var/cache/nginx/client_temp" failed (13: Permission denied)` when the frontend or opportunity_center container starts as `USER 101` on some `nginx:1.25-alpine` base image variants.
- **Root cause:** the alpine base image's default ownership of `/var/cache/nginx/*`, `/var/log/nginx/*`, and `/var/run/nginx.pid` is inconsistent between base image revisions.
- **Fix:** the two Dockerfiles now (a) explicitly `chown -R 101:101` the cache/log directories, (b) redirect the PID file to `/tmp/nginx.pid`, and (c) send error logs to `stderr` — making unprivileged operation robust across base image variants.
- **Files:** `deployment/docker/frontend/Dockerfile`, `deployment/docker/opportunity_center/Dockerfile`.

### Healthchecks: use `127.0.0.1`, not `localhost`
- **Symptom:** `docker inspect` reports containers as `unhealthy` even though `curl http://127.0.0.1/healthz` works fine inside the container. Editing the Dockerfile `HEALTHCHECK` had no effect (see next item).
- **Root cause:** alpine's minimal `/etc/hosts` does not always carry `localhost`; `wget http://localhost/` fails to resolve. The compose healthchecks and the Dockerfile HEALTHCHECKs both used `localhost`.
- **Fix:** all healthchecks (compose + Dockerfile) now use `http://127.0.0.1/…`. Also normalized: both greenfield and shared compose files now hit `/healthz` (v1.0.0 shared compose used bare `/`, which was inconsistent with greenfield).
- **Files:** all Dockerfiles + both compose files.

### Compose healthcheck-override behavior — documented
- **Not a bug — user-observable behavior clarification:** Docker Compose's `healthcheck:` clause overrides the Dockerfile `HEALTHCHECK` at container start time. Editing the Dockerfile alone will not change the effective healthcheck reported by `docker inspect`. This is standard Docker behavior. v1.0.1 aligns the two so they carry the same command (defense-in-depth).

### `.env.shared.example` — MongoDB auth guidance strengthened
- **Symptom:** shared-infrastructure operators deploying alongside an authenticated peer Mongo (e.g., Strategy Factory) hit `Command createIndexes requires authentication` on first backend start.
- **Root cause:** the template's `MONGO_URL` entry described auth-baked URLs as "optional." In real deployments this is required more often than not.
- **Fix:** template text upgraded to `REQUIRED IF PEER MONGO HAS AUTH ENABLED`, with the specific error message and the exact URL pattern to use. Documentation-only change.
- **Files:** `deployment/compose/.env.shared.example`.

## Upgrading from v1.0.0

**Recommended:** re-clone the repo at `v1.0.1` on your VPS and rebuild images from scratch. Data (Mongo volume) is untouched.

```bash
cd /opt/arbicore-x
docker compose -f deployment/compose/docker-compose.yml down       # or docker-compose.shared.yml
git fetch --tags
git checkout v1.0.1
docker compose -f deployment/compose/docker-compose.yml build --no-cache
docker compose -f deployment/compose/docker-compose.yml up -d
make healthcheck
```

**Minimal (compose-only bump):** if your v1.0.0 install is otherwise fine and you only need the healthcheck fix, `docker compose down && docker compose up -d --build` after `git checkout v1.0.1` is sufficient — the mongo data volume is preserved.
